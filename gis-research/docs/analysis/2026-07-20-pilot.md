## Pilot finding: triage token-budget bug (found + fixed mid-pilot)

This is the headline finding of the pilot, not an embarrassment to bury.

- **Attempt 1** (`TOKEN_BUDGET["triage"] = 40_000`, the shipped v2 setting): killed at
  assistant turn 2, **63,174 fresh tokens** — before a single tool call ran. Cold-start
  `cache_creation_input_tokens` alone consumed the entire budget + grace (`50,000`
  threshold). The 40k figure was an estimate that never accounted for cold-start
  prompt-write cost.
- **Fix applied and committed** (commit `037c95d`, `run_agent.py` only): raised
  `TOKEN_BUDGET["triage"]` 40,000 → 80,000, comment: *"cold-start cache write is ~60k+;
  the cap stops runaway work, not boot cost."*
- **Attempt 2** (80k budget, same INR, re-run from clean state): **still killed**, at
  **91,239 fresh tokens** (budget 80,000 + grace 10,000 = 90,000 threshold), turn ~26 of
  work. `triage_findings.json` on disk is the **stale v1-schema file from 2026-07-18**
  (`deep_scan_recommended` bool) — the v2 run never reached T4/T5 to write a fresh
  verdict. Evidence it was not a runaway/blocklist problem: 9 of 10 Bash calls were
  distinct `search.py` invocations (within the ≤10 cap), zero `BLOCKED:` hits, no
  identical-consecutive-call loop — it simply ran out of budget doing legitimate work
  on a genuinely ambiguous project (multiple SPV-name variants: "Hana Springs BESS
  LLC", "Black Mountain Energy Storage", cancellation checks, etc.).

**Conclusion: the 40k→80k fix was necessary but not sufficient.** Ambiguous/SPV-unclear
projects can burn >90k fresh tokens on legitimate T1–T3 work alone. Recommend either
raising the triage budget again (e.g. 120k) or tightening the checklist to cap
search-query fan-out per sub-step — flagged for follow-up, not applied in this pilot
(scope was the one authorized 40k→80k change).

## Deep pilot A — 23INR0086 Hanson Solar (regression)

| metric | value |
|---|---|
| cost | $0.90 |
| turns | 39 (`num_turns`); 60 assistant turns per stream audit |
| tool calls | Read 16, Glob 5, Bash 15, Write 1, Edit 1 — **0 WebFetch** |
| blocklist hits | 0 |
| checkpoints (findings.json touches) | 1 Write, 0 Edits |
| verdict vs expected | **real_active** — matches. Site **31.6950, -99.5315** — exact match to the known-truth ≈31.6950,-99.5315 |

Regression on substance **passes cleanly**. But two literal process criteria **fail**:
findings.json's one-and-only Write happened at **tool call #29** (not ≤5), and only one
Write total (no per-stage cadence). Root cause, confirmed from the stream: Hanson already
had a complete prior deep-scan (dossier.md, imagery, sources, transcripts) on disk. The
agent read the existing artifacts, judged them still valid, and ran a **D5-only refresh**
(`queue_history.py`, `eia_history.py --write`, `build_brief.py`, `build_index.py`, one
`findings.json` schema-completion write) rather than a from-scratch D0–D5 walk. That's a
reasonable, cost-efficient thing for an agent to do on an already-researched project —
but it means the "skeleton-first / checkpoint-per-stage" acceptance bar, which assumes a
fresh run, cannot be validated by this pick alone. Pilot B (below) is the fresh-run test.

## Deep pilot B — 21INR0324 Board Creek Wind (fresh; prior run had crashed)

**Prior (v1-era) attempt, still on disk**: `is_error: true`, exit 143, **460,861 fresh
tokens** (400k budget blown through), **336 WebFetch calls**, `findings.json` and
`dossier.md` both missing — a complete runaway crash, exactly the failure mode v2 exists
to prevent.

**v2 attempt (this pilot)**:

| metric | value |
|---|---|
| cost | $2.72 |
| turns | 100 (`num_turns`); 141 assistant turns per stream audit |
| tool calls | Read 13, Glob 6, Bash 72, Write 5, Edit 3 — **0 WebFetch calls at all** |
| blocklist hits | 0 |
| checkpoints (findings.json touches) | 3 Writes + 3 Edits = 6 |
| longest identical-consecutive tool call | 1 (no stuck-loop motif) |
| verdict | **real_active** — turns out to be a wind farm that has been physically operating on the ERCOT grid since Oct 2022 (EIA plant 65306, 99 turbines, ENGIE VPPA with named offtakers); the GIS queue entry was simply never formally closed out. `cod_assessment.drift_risk = "none"` |

Substantively this is a strong, well-evidenced result and a clean recovery of a run that
previously crashed with zero output, at ~66% of v1's median deep cost and **zero**
WebFetch calls (vs. 336 in the crashed run). Checkpoint discipline is good here (6
findings.json touches vs. Hanson's 1) — because, unlike Hanson, this really was a
from-scratch run.

One literal criterion still **fails**, and it is the **same failure as Hanson**: the
findings.json skeleton write is tool call **#24**, not ≤5. Root cause is identical and
reproducible across both deep runs — the agent's **first** tool call in both cases reads
the wrong absolute path (`/workspaces/scratch-workspace/gis-research/research/PLAYBOOK.md`,
missing the `.claude/worktrees/GIS-research/` worktree segment), then spends ~10 Glob/find
calls locating the correct file before it can even start D0. This is a **systemic prompt
bug, not run-to-run variance** — the `DEEP_PROMPT` template references
`gis-research/research/PLAYBOOK.md` as a path relative to repo root, but the agent's
default assumption of what "repo root" is doesn't match the actual worktree cwd.
Recommend baking the fully-resolved absolute PLAYBOOK/DOSSIER_TEMPLATE paths into the
identity packet.

## Recommendation (evidence only — relaunch is a user decision)

- **Deep mode is a clear win.** Both picks passed on substance: Hanson reproduced the
  known-truth verdict/site exactly, and Board Creek recovered a run that had crashed
  outright under v1 (336 WebFetch calls, no output) into a clean, well-evidenced
  completion at ~66% of the v1 median cost with zero WebFetch calls. The two process
  misses (skeleton-write timing) trace to one fixable prompt bug (unresolved PLAYBOOK
  path), not a design flaw, and checkpoint cadence is fine on a genuine from-scratch run
  (Board Creek: 6 touches).
- **Triage mode is not yet relaunch-ready.** The 40k budget was a real bug (fixed,
  committed as `037c95d`), but even at 80k a legitimately ambiguous project still blew
  the budget before writing v2-schema output. Recommend a further budget increase and/or
  tighter search fan-out in `TRIAGE_CHECKLIST.md` before resuming the triage fleet at
  scale, and re-validating on 2–3 more ambiguous picks.
