## Pilot finding: triage token-budget bug (found + fixed mid-pilot)

This is the headline finding of the pilot, not an embarrassment to bury.

- **Attempt 1** (`TOKEN_BUDGET["triage"] = 40_000`, the shipped v2 setting): killed at
  assistant turn 2, **63,174 fresh tokens** — before a single tool call ran. Cold-start
  `cache_creation_input_tokens` alone consumed the entire budget + grace (`50,000`
  threshold). The 40k figure was an estimate that never accounted for cold-start
  prompt-write cost.
- **Fix applied and committed** (commit `037c95d`, `run_agent.py` only): raised
  `TOKEN_BUDGET["triage"]` 40,000 → 80,000, comment: *"cold-start cache write is ~60k+;
  the cap stops runaway work, not boot cost."*
- **Attempt 2** (80k budget, same INR, re-run from clean state): **still killed**, at
  **91,239 fresh tokens** (budget 80,000 + grace 10,000 = 90,000 threshold), turn ~26 of
  work. `triage_findings.json` on disk is the **stale v1-schema file from 2026-07-18**
  (`deep_scan_recommended` bool) — the v2 run never reached T4/T5 to write a fresh
  verdict. Evidence it was not a runaway/blocklist problem: 9 of 10 Bash calls were
  distinct `search.py` invocations (within the ≤10 cap), zero `BLOCKED:` hits, no
  identical-consecutive-call loop — it simply ran out of budget doing legitimate work
  on a genuinely ambiguous project (multiple SPV-name variants: "Hana Springs BESS
  LLC", "Black Mountain Energy Storage", cancellation checks, etc.).

**Conclusion at the time: the 40k→80k fix was necessary but not sufficient.** A second
fix round was authorized: `TOKEN_BUDGET["triage"]` 80,000 → 120,000 (commit `db8d147`,
comment: cost stays ~$0.40/run either way since cap ≠ spend), plus tightening
`TRIAGE_CHECKLIST.md` T3 to ≤6 `search.py` calls (was ≤10), at most one WebFetch of a
result page (only if decisive), and a hard verdict deadline at assistant turn 20
(default `ambiguous` if still uncertain). The same commit also fixed both prompts to
inject fully-resolved **absolute** paths for `TRIAGE_CHECKLIST.md`/`PLAYBOOK.md`/
`DOSSIER_TEMPLATE.md`/the Hanson dossier example, closing the path-confusion bug found in
both deep pilots (see Deep pilots A/B below).

- **Attempt 3** (120k budget, tightened T3, absolute paths, re-run from clean state):
  **still killed** — and *faster* than attempt 2: turn ~4, **141,752 fresh tokens**
  (budget 120,000 + grace 10,000 = 130,000 threshold), with only **2 tool calls executed**
  (1 Read, 1 Bash). This did not fit the "legitimate work consumed the budget" story from
  attempt 2 — barely any work had happened. `total_cost_usd` for the run was only **$0.125**,
  which is not possible if 141,752 real fresh tokens had actually been spent. That
  contradiction was the tell.

### Root cause, finally: a token-counting bug, not a budget-sizing problem

Tracing the raw `run_stream_triage.jsonl` for attempt 3: the CLI emits **one JSONL
`"assistant"` line per content block** of a single logical turn (`thinking`, `text`,
`tool_use`, ...), and every one of those lines carries the **same `message.id`** and the
**same cumulative usage snapshot** for that turn. `run_agent.py`'s live spend-accumulator
(and the post-run `validate()` turn-counter) summed/counted **every line**, so one real
turn with 4 content blocks got its usage added 4 times. Confirmed directly: 4 stream lines
sharing `message.id = msg_bdrk_01HajwBnKTpp2vXDhhxdgEYy`, each reporting identical
`cache_creation_input_tokens: 32265` — summed as if it were 4 separate 32k turns instead
of one. Deduplicating by `message.id` on that same recorded stream drops the "141,752
tokens" run down to a consistent **38,600 real fresh tokens for 2 real turns** — in line
with the $0.125 actual cost.

This retroactively reframes attempts 1 and 2 as well: the "cold-start ~63k" figure used to
justify the first budget bump was itself inflated by this bug (a single real cold-start
turn is closer to ~32k), and both the 40k and 80k triage kills were **largely artifacts of
the counting bug, not genuine budget exhaustion** — the triage budget was never actually
the binding constraint.

**Fix** (commit `0adf6c5`, `run_agent.py` only): track a `seen_msg_ids` set in both the
live accumulator in `main()` and in `validate()`; sum a turn's usage / increment the turn
counter only the first time its `message.id` is seen. `tool_counts`/`image_reads` were
**not** affected by the bug (each `tool_use` content block appears on exactly one stream
line) and did not need changing — every line is still logged and scanned for those.
Verified against the disk copy of attempt 3's stream before re-running (see above:
38,600 deduped vs. $0.125 cost — consistent).

- **Attempt 4** (same INR, with the counting-bug fix applied): **PASS.** Exit 0, no
  violations. `fresh_tokens = 45,148` (well under both the new 120k budget *and* the
  original 40k). Cost **$0.446**, `num_turns = 19` (13 deduped assistant turns). 7 distinct
  `search.py` calls (target was ≤6 — a narrow, honest miss by one call), 0 WebFetch calls,
  0 blocklist hits. `triage_findings.json` is v2-schema and **fresh** (dated 2026-07-20,
  mtime confirms overwrite of the stale 2026-07-18 file): `"verdict": "ambiguous"`,
  `"score_adjustment": {"delta": 0, "citation": null}` — a defensible verdict given the
  evidence (7 searches, all either negative or one unconfirmed developer lead; no IA, no
  Ch.313 match, no construction visible; consistent with the factsheet's own `ambiguous`
  gate call).

**Note on the two deep pilots below**: both were run *before* the message.id
double-counting bug was found and fixed, so their reported `fresh_tokens`/`assistant_turns`
were inflated by the same bug (~2× — see the root-cause writeup above). Both deep runs
still exited 0 (success) under the inflated numbers because 218k/304k were still well
under the 400k+10k deep budget, so **the bug never falsely killed either deep run** —
only the reported figures needed correcting, which is done below (deduped values shown
alongside the original reported ones). Cost, tool_counts, verdicts, and checkpoint counts
were never affected by the bug and stand as originally reported. Per-run re-execution of
the deep pilots was not repeated — not needed, since neither was a false result.

Regression on substance **passes cleanly**. But two literal process criteria **fail**:
findings.json's one-and-only Write happened at **tool call #29** (not ≤5), and only one
Write total (no per-stage cadence). Root cause, confirmed from the stream: Hanson already
had a complete prior deep-scan (dossier.md, imagery, sources, transcripts) on disk. The
agent read the existing artifacts, judged them still valid, and ran a **D5-only refresh**
(`queue_history.py`, `eia_history.py --write`, `build_brief.py`, `build_index.py`, one
`findings.json` schema-completion write) rather than a from-scratch D0–D5 walk. That's a
reasonable, cost-efficient thing for an agent to do on an already-researched project —
but it means the "skeleton-first / checkpoint-per-stage" acceptance bar, which assumes a
fresh run, cannot be validated by this pick alone. Pilot B (below) is the fresh-run test.

| blocklist hits | 0 |
| checkpoints (findings.json touches) | 3 Writes + 3 Edits = 6 |
| longest identical-consecutive tool call | 1 (no stuck-loop motif) |
| verdict | **real_active** — turns out to be a wind farm that has been physically operating on the ERCOT grid since Oct 2022 (EIA plant 65306, 99 turbines, ENGIE VPPA with named offtakers); the GIS queue entry was simply never formally closed out. `cod_assessment.drift_risk = "none"` |

Substantively this is a strong, well-evidenced result and a clean recovery of a run that
previously crashed with zero output, at ~66% of v1's median deep cost and **zero**
WebFetch calls (vs. 336 in the crashed run). Checkpoint discipline is good here (6
findings.json touches vs. Hanson's 1) — because, unlike Hanson, this really was a
from-scratch run.

One literal criterion still **fails**, and it is the **same failure as Hanson**: the
findings.json skeleton write is tool call **#24**, not ≤5. Root cause is identical and
reproducible across both deep runs — the agent's **first** tool call in both cases reads
the wrong absolute path (`/workspaces/scratch-workspace/gis-research/research/PLAYBOOK.md`,
missing the `.claude/worktrees/GIS-research/` worktree segment), then spends ~10 Glob/find
calls locating the correct file before it can even start D0. This is a **systemic prompt
bug, not run-to-run variance** — the `DEEP_PROMPT` template references
`gis-research/research/PLAYBOOK.md` as a path relative to repo root, but the agent's
default assumption of what "repo root" is doesn't match the actual worktree cwd.
Recommend baking the fully-resolved absolute PLAYBOOK/DOSSIER_TEMPLATE paths into the
identity packet.

## Recommendation (evidence only — relaunch is a user decision)

- **Deep mode is a clear win.** Both picks passed on substance: Hanson reproduced the
  known-truth verdict/site exactly, and Board Creek recovered a run that had crashed
  outright under v1 (336 WebFetch calls, no output) into a clean, well-evidenced
  completion at ~66% of the v1 median cost with zero WebFetch calls. The two process
  misses (skeleton-write timing) trace to one fixable prompt bug (unresolved PLAYBOOK
  path) that has since been fixed (`db8d147`, absolute paths injected into both prompts)
  but not re-validated with a fresh deep run — recommend one quick from-scratch deep pilot
  before fleet relaunch to confirm the skeleton-within-5-calls bar is now met. Checkpoint
  cadence is fine on a genuine from-scratch run (Board Creek: 6 touches).
- **Triage mode is now much closer to relaunch-ready, but the path there was not a
  simple budget bump.** The real story: three of four fix attempts (40k, 80k, then 120k
  budget) all still "failed" — but by attempt 3 it became clear the budget was never the
  actual constraint. A token-counting bug (the CLI streams one line per content block,
  all sharing one `message.id`; the runner summed every line) was inflating both the live
  spend counter and the post-run turn audit by roughly the blocks-per-turn factor,
  producing spurious kills at 63k/91k/141k tokens when real spend was ~32–39k. Once fixed
  (`0adf6c5`) and combined with the T3 tightening, attempt 4 passed cleanly at **$0.446 /
  19 turns**, comfortably under both the new 120k budget and the original 40k figure.
  One narrow miss remains: 7 `search.py` calls vs. the tightened ≤6 target — recommend
  either loosening to ≤7 or re-checking T3's phrasing, then validating on 2–3 more
  ambiguous picks (with genuine budget numbers now that the counting bug is fixed) before
  a full fleet relaunch.
