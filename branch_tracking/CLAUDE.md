# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

In-progress design for a topology database table that tracks transmission branches over time — identity, status, in-service/retirement dates, and CIM model linkage. Scoped to ERCOT only: any query against `BRANCH` (or similar source tables) filters `isomarketid = 6` and always will.

**`teid` is the grain.** It's ERCOT's own authoritative per-component identifier, not a database surrogate — so the tracking table is keyed on `teid`, one row per `teid`, even where the underlying `BRANCH` table has more than one candidate row for it. `branch_id` (SQL Server `BRANCH.branchID`) is just an attribute of that row, not the identity. This was deliberately reconsidered mid-project (an `advisor` consultation suggested keying on `branch_id` instead, reasoning that status/date columns are per-physical-row) and reverted — `branch_id` is a source-system surrogate that can be duplicated, superseded, or occasionally mistagged, so it can't be the grain. See "Known `BRANCH` data-quality issues" below for concrete examples of why.

## Code layout (post phase-1)

- `pipeline/` — 8 pure-logic modules, no DB access: `config`, `naming`, `mapping`, `legs`, `dates`, `dampsse`, `status`, `assemble`. Imported by scripts via a `sys.path` bootstrap (no packaging yet — that's phase 5).
- `scripts/` — the original entry points are now thin wrappers around `pipeline/`: DB pulls + prints + CSV writes only. Every existing `uv run branch_tracking/scripts/<name>.py` invocation still works unchanged.
- `scripts/adhoc/` — one-off investigation scripts, out of production scope, moved here verbatim.
- `tests/` — test files (under `branch_tracking/`), including a golden byte-identity gate (`test_goldens.py`) and fixture-based regression pins for hand-verified marquee teids. Run with `uv run pytest` from the repo root (`testpaths` points here).

Full docs restructure is deferred to phase 5; this section is just an orientation pointer for phase 1.

## Hard rule — do not touch the live database

This folder only ever produces:
- SQL DDL (`CREATE TABLE ...`) for the proposed tracking table.
- CSV output artifacts, generated locally, for the user to inspect and upload themselves.

Never create the table against the actual database and never run `INSERT`/`dfInsert`/`dfInsertAlchemy` against it from this folder's work. Read-only `SELECT`s against source tables (e.g. `dbo.BRANCH`) for schema/data investigation are fine via the `awconnect` skill.

## Scripts

All investigation/working scripts for this folder live under `scripts/`, checked into the repo — never in `/tmp` or the scratchpad. Run them with `uv run branch_tracking/scripts/<name>.py` from the repo root (see the top-level `CLAUDE.md` for why plain `uv run` is enough here, regardless of any `VIRTUAL_ENV` set in the shell).

- `scripts/explore_branch_schema.py` — BRANCH/PTOBRANCH schema + sample via Snowflake (`AW.DBO`).
- `scripts/explore_branch_sqlserver.py` — same investigation via SQL Server (`awconnect.db`, `dbo.BRANCH`). Kept alongside the Snowflake version because the two sources disagree — see "Source discrepancy" below.
- `scripts/build_teid_branchid_map.py` — the main pipeline. Joins the CIM CSV's `Branch`/`Transformer` rows (`TransmissionElementId` == `teid`) against SQL Server `dbo.BRANCH`, then resolves `BRANCH.teid` duplicates down to one `branch_id` per `teid` through five layered steps (each documented in the module docstring, in order): exclude `collapseId`-superseded rows; exact `OP_EQCODE`/`OpEqName` match; collapse exact-duplicate re-insertions (keep highest `branch_id`); fuzzy-name match (calibrated `SequenceMatcher` ratio) for naming-convention variants; and a high-side-preferred + latest-`branch_id` catch-all for transformer winding-leg pairs. Produces `output/teid_branch_id_map.csv` with a `match_status` column recording which step resolved each row, plus an `opeq_agrees` QA flag on every row (including clean 1:1 matches) for spot-checking.
- `scripts/analyze_unmatched.py` — classifies the `teid`s with no `BRANCH` match at all (see "Unmatched teids" below).
- `scripts/analyze_duplicate_teids.py` / `..._snowflake.py` — earlier investigation into *why* `BRANCH.teid` has duplicates in the first place (superseded-row re-numbering vs genuine collisions), before the resolution pipeline above was built. Still useful background, superseded as the primary mapping path by `build_teid_branchid_map.py`.
- `scripts/analyze_duplicate_opeqcode.py` — early exploration of using `OP_EQCODE` to disambiguate 2-candidate duplicates; the logic here was folded into `build_teid_branchid_map.py`'s step 2.
- `scripts/build_transformer_leg_map.py` — surfaces BOTH the high-side and low-side `BRANCH` row for every Transformer `teid` (the main map only keeps one winner), including legs whose sibling has a NULL `teid` in `BRANCH` and had to be found by name/bus-pair matching. Run AFTER `build_teid_branchid_map.py`.
- `scripts/find_collapseid_fix_candidates.py` — recommends real `BRANCH` DB fixes: `Line`/`Transformer` rows that are the same physical element inserted more than once with no `collapseId` link. Scans all of `BRANCH` (not just the CIM-relevant subset), restricted to `DeviceType IN ('Line', 'Transformer')`.
- `scripts/find_teid_collision_candidates.py` — manual-review worklist of rows sharing a `teid` with something that doesn't fit any validated pattern (not a confirmed duplicate, not a legitimate leg pair) -- these likely need the `teid` *value* itself corrected. Depends on the two scripts above already being run (treats their output as the "already explained" baseline).
- `scripts/build_branch_default_status.py` — first-cut `default_status` (normally closed/open) approximation from recent `PTOBRANCH` snapshots; see "Design intent" below for caveats. A stopgap until the in-service-date/outage-based approach is built.
- `scripts/explore_outage_schema.py` / `explore_outage_lookups.py` — schema/data exploration for the outage tables (`toChangesAllIsos`, `toState`, and their lookup tables `toReason`/`toCause`/`toOutageType`/`toStatus`). `dbo.toAllIsos` was in scope initially but the user confirmed it's an hourly-snapshot dump full of duplicates, not useful here -- dropped from the investigation entirely. Key finding: `toOutageTypeId`/`outageTypeID` are NULL for every ERCOT row; `dbo.toReason` (`ReasonID`) is what actually distinguishes "New Equipment Energization" (4) and "Retirement of Old Equipment" (9).
- `scripts/build_inservice_retirement_dates.py` — first-cut `in_service_date`/`retirement_date` per `teid`, from `toChangesAllIsos` events with `ReasonID IN (4, 9)`. See "Design intent" below for method and caveats.
- `scripts/inspect_teid_energization_example.py <teid>` — ad hoc diagnostic (not part of the regular pipeline) that dumps a single teid's raw `ReasonID=4` ticket history, including `BranchId`/`EquipmentName`. Used to find the chained-ticket, BranchId-bundling, and sticky-date patterns described in the `in_service_date` design-intent entry below; handy for spot-checking any teid flagged in `teid_inservice_retirement_dates.csv`.
- `scripts/review_multiple_energization_chains.py` — ad hoc batch reviewer (not part of the regular pipeline) for the `multiple_confirmed_energization_events` bucket; pulls all flagged teids' events in one combined query and reuses the main script's own filtering/chain logic. Output: `output/multiple_energization_review.csv`.
- `scripts/investigate_retirement_flags.py` — ad hoc investigator (not part of the regular pipeline) for `multiple_confirmed_retirement_events` and (formerly) `retirement_before_inservice`; pulls ALL revisions and ALL ReasonID values (not just 4/9) for the flagged teids in one combined query, to directly test hypotheses like ReasonID reclassification. Output: `output/retirement_flags_investigation.csv`.
- `scripts/build_final_branch_table.py` — consolidates everything into `output/branch_tracking_table.csv` (one row per CIM teid: `teid`, `branch_id`, `ercotDampsseId`, buses, ckt, both status sources, dates). Pure local join, no DB.
- `scripts/explore_rt_rating_dampsse_schema.py` — schema exploration for the ERCOT RT dynamic rating tables (`ercotRtDynamicRating*` — link by `elementTEID`/`RDFID`/`branchID`, 15-min cadence) and DAM PSSE tables (`ercotDampsse*` — hourly `inService` back to 2015, keyed `(awDateID day-serial, HE, ercotDampsseId)`, NO teid/rdfid: linkage is name/station-based).
- `scripts/build_dampsse_default_status.py` — DAM PSSE `inService`-based `default_status` (2-year dominant status; per the user, a better indicator than the auction snapshots). Exact-name mapping tier; caches DAM dims + the aggregate to `data/raw/` for DB-free follow-ons. Output: `output/dampsse_default_status.csv`.
- `scripts/map_unmapped_dampsse_teids.py` — DB-free fallback mapping tiers (substring name, station-pair, transformer leg-aware; fileType-filtered) for teids the exact-name tier missed, plus a diagnosis of what remains. Outputs: `output/dampsse_fallback_mappings.csv`, `output/dampsse_unmapped_diagnosis.csv`, `output/dampsse_default_status_fallback.csv`.
- `scripts/compare_base_model_status.py <export.csv>` — one-off comparison of our status vs a PowerWorld base-model export (label columns classified by format: integer=teid, UUID=rdfid). Outputs: `output/base_model_status_comparison.csv` / `..._outages_...csv`.

## Current status (as of the teid→branch_id mapping work)

`output/teid_branch_id_map.csv` maps **10,927 of 11,443 (95.5%)** CIM branch/transformer `teid`s to exactly one `branch_id`. The remaining 516 are unmatched (see below) — not a gap in the resolution logic, they genuinely have no `BRANCH` row. Follow-on artifacts built on top of that map: `transformer_leg_map.csv` (both transformer legs), `collapseid_fix_candidates.csv` and `teid_collision_candidates.csv` (BRANCH data-quality fix/review lists), a first-cut `default_status` in `branch_default_status.csv`, a first-cut `in_service_date`/`retirement_date` in `teid_inservice_retirement_dates.csv` (see "Design intent" below for both), and now a **consolidated `output/branch_tracking_table.csv`** (`teid`, `branch_id`, `from_bus`, `to_bus`, `ckt`, `implied_default_status`, `in_service_date`, `retirement_date`, one row per all 11,443 CIM teids) joining the three together via `build_final_branch_table.py`. This consolidated table is a **starting point for validation, not a finished product** — current open issues (per the user):
  1. Retirement dates derived from outages need cross-validation against `implied_default_status` — confirmed via `teid=1019`: resolved `retirement_date=2021-10-18`, but `implied_default_status=Closed` at `pct_closed=1.0` (100% closed in recent auction snapshots) and the device still appears in the current July 2026 CIM model. The underlying "retirement" tickets were both very short (hours), suggesting a mis-tagged maintenance outage, not a real decommissioning.
  2. The same cross-validation is needed for `in_service_date` against energization evidence.
  3. `implied_default_status` itself needs validation, particularly normally-open (`Open`-majority) cases — genuinely normally-open device (reactor/capacitor bypass, PST) vs. just heavily sampled during outages.
  Not yet started: the `CREATE TABLE` DDL for the tracking table itself.

### Unmatched teids (516) — not a real gap

Two CIM-modeling artifacts explain nearly all of them (`scripts/analyze_unmatched.py`):
1. **Transformer tertiary-winding stubs** — a `Transformer` row whose low-voltage terminal is a fictitious ~1kV star/dummy point (3-winding transformer CIM decomposition artifact). `BRANCH` only carries the primary/secondary 2-winding equivalent.
2. **Generation-plant-internal equipment** — collector-system/reactor elements (solar, wind, battery, industrial cogen, station-load) behind a generator interconnection point, never represented in the bulk-transmission `BRANCH` table.

### Known `BRANCH` data-quality issues (found while resolving duplicates)

- **A transformer's sibling winding-leg row can have a NULL `teid`.** Example: DIB substation's `DIB_MT2H` correctly carries `teid=280262`, but its low-side sibling `DIB_MT2L` has `teid = NULL` in `BRANCH` — it can never be joined to via `teid` no matter what the script does, because the join key is missing on the source side. This means some legitimate leg rows are permanently unreachable through this mapping approach.
- **A `branch_id` can be mistagged with the wrong `teid`.** Example: same DIB substation, `DIB_MT1` (branch_id 60081599, a genuinely different device — its own bus pair doesn't match either MT1's or MT2's real pair) carries `teid=280262`, which should belong only to `DIB_MT2H`. The resolution pipeline's high-side-preference rule happened to exclude it correctly, but this is a real upstream data error, not something the script detects specifically.
- **Naming inconsistency can look like "different transformers" when it isn't.** Vealmoor's `VEALMOOR_VLM7TR2H` (high side) and `VEALMOOR_VLMTR2L` (low side, missing a "7" in the name) both correctly carry `teid=39798` — same asset, just an inconsistently-named low-side row. Trust the `teid` tag over apparent naming differences when they conflict; verify against raw rows before concluding two candidates are unrelated (see PTOBRANCH/BRANCH investigation methodology below).
- Given the above, don't assume every remaining "duplicate" or "unmatched" `teid` is fully explained — spot-check surprising cases against the raw `BRANCH` rows (and `PTOBRANCH` where relevant) before trusting an automated classification.
- **`dbo.toAllIsos` is an hourly-snapshot dump, not a source of outage records.** It repeats the same outage row once per hour it was active (confirmed: 32,059 rows for a single teid), and an unfiltered `GROUP BY` against it hangs/times out. Use `dbo.toChangesAllIsos` instead (one row per outage revision, has its own `teid` column) plus `dbo.toState` for status lookups.
- **`toAllIsos.outageTypeID` / `toState.toOutageTypeId` are NULL for every ERCOT row.** These look like the obvious "outage type" field but aren't populated for isomarketid=6 at all (2.17M `toState` rows checked, all NULL) — likely only used by other ISOs (see the adjacent `caiso*` columns). The actual "new equipment" vs "retirement" signal lives on `dbo.toReason.ReasonID` instead (4 = "New Equipment Energization", 9 = "Retirement of Old Equipment") — see `build_inservice_retirement_dates.py`.

### Source discrepancy: SQL Server vs Snowflake

`dbo.BRANCH` (SQL Server) and `AW.DBO.BRANCH` (Snowflake) are supposed to mirror each other but don't agree — different row counts (122,259 vs 129,635 for `isomarketid=6`), different duplicate-`teid` counts (7,523 vs 13,596), different column casing (camelCase vs ALL CAPS) and nullability. **The mapping pipeline uses SQL Server as the source of truth**; this was never fully reconciled, just decided pragmatically. Worth revisiting if SQL Server access becomes unreliable again.

## Design intent (from thoughts.md, the user's original plan)

- **Identity — `branch_id` + `teid`**: core identity columns, with `teid` as the actual grain (see "Purpose" above). Cross-checking requires going `branch_id` → `PTOBRANCH` (via `PTOBRANCH.branchID`) to get the from/to bus number — `PTOBRANCH` has very sparse coverage though (only ~12.7% of `BRANCH` rows have any `PTOBRANCH` entry at all, and where present it can have hundreds of historical-looking rows per `branchID` with no timestamp column to pick "current" from other than the surrogate `ptoBranchID` itself).
- **`status`**: sourced from DAM (Day-Ahead Market), or potentially from finding the matching outage for physical (actual) state. Open question: is there a secondary confirmation source (60-Day SCED data / DAM network model)?
- **`in_service_date`** / **`retirement_date`**: first-cut approximation built (`build_inservice_retirement_dates.py`, `output/teid_inservice_retirement_dates.csv`, flagged subset also in `output/inservice_retirement_review_flags.csv`). Method: pull `AW.dbo.toChangesAllIsos` events with `ReasonID` 4 ("New Equipment Energization") or 9 ("Retirement of Old Equipment") -- the field the user originally described as "outage type new/retirement" turned out to live on `ReasonID`, not `outageTypeID`/`toOutageTypeId` (both NULL for every ERCOT row).
  - **Sticky actual dates**: forward-fill `actualStartDate`/`actualEndDate` within each `(toOutageIdentifierId, BranchId)` ticket's own revision history before collapsing to the highest `toStateId`. Fixes a real bug found via `teid=1743`: a ticket's *final* revision (a purely administrative `status='RatE'` update) had blank actual dates even though an *earlier* revision genuinely recorded them, making a real 8-month commissioning look unconfirmed. This one fix alone dropped `energization_planned_not_actualized` from 856 to 294 -- it was silently degrading confidence far beyond just this one teid.
  - **BranchId cross-check**: `teid=70365`'s outages tagged both `CEDH_OAKC11` (branch_id 60003752) and `CEDRHI_OAKC11` (branch_id 60008059, the one this teid actually maps to per `teid_branch_id_map.csv`), because ERCOT bundled their commissioning into the same clearance windows. Events whose `BranchId` disagrees with the teid's mapped branch_id are dropped (425 rows); a NULL `BranchId` passes through unfiltered.
  - **Device-name cross-check**: the SAME `BranchId` can be referenced under different informal `EquipmentName` strings across different tickets/years (unlike the bundling case above, so `BranchId` alone doesn't catch it). Confirmed via `teid=317479`: its CIM-confirmed device normalizes to a match on a 1-minute outage ticket (`6520_G`), while a much longer, unrelated chain (`PS0`) shares the same teid -- "longest duration wins" alone picked `PS0`. Each event's `EquipmentName` is normalized (strip to uppercase alphanumeric only, literal placeholders like `"BLANK"` treated as unknown) and compared against the teid's normalized `OpEqName`/`branch_name` using **substring containment**, not exact equality -- the outage system very commonly records only the short device tag (e.g. `"T1"`, `"MR2H"`, `"XT4"`) while CIM's name is the full Substation+Device string (e.g. `"BKSLESST1"`, `"EXCSWMR2H"`). This wasn't a minor tweak: an initial exact-equality version was validated against a sample of 1,104 initially-dropped teids and 88% (977) were exactly this abbreviation pattern -- exact equality would have discarded the large majority of genuinely correct evidence. A CONFIRMED mismatch (neither name contains the other) is dropped outright wherever it occurs, the same way a BranchId mismatch is -- confirmed via `teid=113628`, whose CIM device is `"AT2H"` (a transformer winding) but EVERY one of its retirement tickets tags `EquipmentName="CB_1814"` (a circuit breaker, no substring relation): a breaker being retired doesn't mean the transformer position it protects was retired. No matching evidence means no evidence, not "trust whatever's left." When there IS remaining evidence and multiple genuinely separate chains exist, name-matching chains are still preferred as a secondary tie-break.
  - **ERCOT start/end convention**: for energization, the relevant date is the outage's END (`actualEndDate`, falling back to `plannedEndDate`) -- confirmed via `teid=552333` (equipment came into service in December 2022, the chain's END, not its January start) and `teid=555249` (a unit's return-to-service can be tracked via a new "energization" ticket even when not literally new construction -- flagged as an unmodeled special case). For retirement, the relevant date is the outage's START.
  - **Chain detection**: a single real energization/commissioning process routinely spans multiple outage tickets that expire and get re-ticketed -- `teid=527244`'s "Delilah" substation commissioning ran Oct 2021 → Dec 2023 across 9 tickets. Consecutive events within `CHAIN_GAP_TOLERANCE` (3 days) collapse into one chain; energization reports the chain's **overall end**, retirement its **first start**.
  - When genuinely separate chains remain (restricted to name-matching chains first, if any -- see above): **energization** picks the **longest-duration** chain (confirmed via `teid=552333`); **retirement** still takes the **latest chain**.
  - **Mis-tag correction**: if the resolved retirement predates the resolved energization AND both resolve to the SAME device (normalized name match), the retirement was never real -- it's a ticket incorrectly tagged "Retirement of Old Equipment" and corrected by a proper energization ticket for the same equipment shortly after. Confirmed via `teid=821` and `teid=654439` (exact device-name match, energization minutes-to-days after the "retirement"); `retirement_date` is reverted to the `2099-12-31` default in this case (2 teids corrected). For the genuinely-different-device case (e.g. `teid=121320`/`185126`/`198761`/`207211`/`317479`: the retirement's device is a clearly different, old piece of equipment -- literally named `DELETE` or `OLD1303_SW` -- while the energization's device matches the teid's current CIM name), the device-name cross-check above already drops that stale retirement evidence entirely, so these resolve cleanly to `ok` (retirement defaulted) rather than needing a separate informational flag -- an earlier version surfaced these as `teid_reused_after_retirement`, but once the device-name filter was corrected, that flag mostly disappeared on its own (down to 1 teid: `teid=1743`, whose old and current devices -- `ARPTMARYAT11` vs `GS2Y` -- genuinely share no substring relation, a real historical teid reuse worth keeping visible).
  - Defaults to `1990-01-01` / `2099-12-31` when no valid matching event exists. Every teid still gets a best-guess date regardless of its flag rather than blocking on ambiguity -- the flagged subset is written separately to `inservice_retirement_review_flags.csv` (612 teids) as a manual-review worklist. Per the user: `multiple_confirmed_energization_events`, `retirement_found_no_energization`, and `energization_planned_not_actualized` are accepted as resolved and not pursued further (a follow-up batch review via `scripts/review_multiple_energization_chains.py` / `output/multiple_energization_review.csv` found the bundled-device pattern was rare -- most were genuine multi-year, multi-phase projects). `multiple_confirmed_retirement_events` (8 teids) got a first-pass investigation (`scripts/investigate_retirement_flags.py`, `output/retirement_flags_investigation.csv`) showing multi-step decommissioning processes (switching operations spaced weeks to years apart, sometimes a cancelled false start first, sometimes a coordinated multi-device project sharing a group/project number), not mis-tagging -- current "latest chain wins" resolution looks correct, not pursued further.
  - **Retirement-vs-status contradiction correction**: joins `branch_default_status.csv`'s `implied_default_status` (recent `PTOBRANCH` auction-snapshot evidence) against every resolved retirement. Digging into `teid=1019` and `teid=3830` (flagged for review, then investigated in detail) found the retirement was almost certainly bogus: `teid=3830` was "retired" in 2015 via a single outage ticket, yet showed 100% Closed across all 20 recent (2025-2026) auction snapshots — a full decade of continuous operation *after* its claimed retirement. Broadening the check found **83% of all resolved retirements (131 of 158) initially contradicted a Closed status** — including clusters of *different* teids sharing the exact same retirement timestamp in tight name-related groups (e.g. one transformer's H/L legs both "retired" at the same minute; several circuits at the same substation), a clear signature of coordinated substation-wide maintenance/equipment-replacement work being tagged "Retirement of Old Equipment," not individual permanent decommissioning. When status evidence is confident (`status_review_flag='clear_majority'`, Closed, backed by >= `STATUS_CONTRADICTION_MIN_ROWS` (5) recent snapshots), the retirement is reverted to the default (101 corrected); weaker contradictions are left as-is but flagged `retirement_status_uncertain` (30) rather than silently corrected. `teid=1019`/`teid=3830` both now correctly resolve with `retirement_date_source='default'`.
  - Of 10,927 teids (final run, all fixes applied): 4,627 (42.3%) have a valid energization event, 57 (0.5%) have a valid retirement event surviving the status cross-check; `review_flag` breakdown: `ok` 10,269 (94.0%), `energization_planned_not_actualized` 286 (2.6%), `multiple_confirmed_energization_events` 218 (2.0%), `evidence_dropped_wrong_device` 109 (1.0%), `retirement_status_uncertain` 29 (0.3%), `multiple_confirmed_retirement_events` 8 (0.1%), `retirement_found_no_energization` 7 (0.1%), `teid_reused_after_retirement` 1 (<0.1%).
  - Known limitations: for teids with no valid ReasonID=4/9 event at all, the `1990-01-01` default does NOT mean "known to be in service since 1990" -- it means no outage-based evidence either way. The cancellation keyword list and the BranchId/device-name cross-checks only catch what's populated -- a NULL field on either side passes through unfiltered. `CHAIN_GAP_TOLERANCE` (3 days) is a judgment call -- 527244's real chain gaps were all 0-1 minutes, so there's room to tighten it if it ever looks like it's over-chaining unrelated events.
- **`default_status`**: closed or normally open. First-cut approximation built (`build_branch_default_status.py`, `output/branch_default_status.csv`): tally `PTOBRANCH.branchStatus` (`Closed`/`Open`) across the last ~20 ERCOT Monthly Auction cases (`AW.dbo.ptoFile`, 2025-2026, non-CIM) per `branch_id`, take the majority. Of 10,927 branches: 92.7% have a clear majority either way (10,323 Closed / 324 Open, matching the expectation that normally-open devices -- reactor/capacitor bypasses, PSTs -- are a small minority), 4.8% are `mixed` (roughly even split, needs manual review -- could be a genuine normally-open device or just a lot of sampled outages), 2.6% have zero recent `PTOBRANCH` coverage. Known limitation: doesn't dedupe multiple rows for one branch within a single snapshot when its bus is split in that case's model. This is explicitly a stopgap, to be superseded once the in-service-date/outage-data approach above is built.
- **`cim_id`**: initially scoped to just the July CIM model (this folder's CSV). Designed to extend to searching for the earliest matching entry by the `TEID + RDFID + (r, x, b)` electrical-parameter tuple.
