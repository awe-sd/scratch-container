# output/ — CSV artifacts

Generated by the scripts in `../scripts/`, from read-only queries against SQL Server `dbo.BRANCH`/`dbo.PTOBRANCH` (`isomarketid = 6`, ERCOT) and the CIM CSV in `../data/`. Nothing here is ever written back to a live database. See `../thoughts.md` ("Investigation Findings") and `../CLAUDE.md` for full narrative detail — this is just a quick index of what each file is.

## Primary deliverables

**`branch_tracking_table.csv`** — the consolidated tracking table: one row per CIM `teid` (all 11,443, including the ~516 unmatched ones -- 3rd-winding/generation-step-up stubs etc. still appear as rows, just without a `branch_id`/bus/`ckt`). Identity: `teid`, `branch_id`, `ercotDampsseId` (99%+ mapped). **`default_status`** is the resolved status -- DAM PSSE `inService` dominant status is primary (`default_status_source='dampsse_inservice'`, 10,907 rows), the auction-based value only a fallback (`'auction_fallback'`, 12 rows), blank when neither knows (524); the per-source columns (`dampsse_default_status`/`dampsse_pct_inservice`, `implied_default_status`/`pct_closed`) are kept alongside for audit. Dates from `teid_inservice_retirement_dates.csv` (defaulted `1990-01-01`/`2099-12-31` where missing). A pure local-file join, no DB query. Built by `build_final_branch_table.py`.

**`PINNED_unmapped_dampsse.md`** — the parked worklist: the 20 teids with no DAM status (parallel units with disagreeing candidate statuses, DAM-dormant elements, GSU stubs, LOTEBUSH), the 73 consensus-status/identity-ambiguous teids, and the deferred mechanisms (impedance tier, RT-rating crosswalk, outage cross-check, auction snapshot discounting). Pinned 2026-07-09 to revisit later.

**`teid_branch_id_map.csv`** — the core output: one row per CIM `Branch`/`Transformer` element, mapped to a single `branch_id` in `BRANCH` wherever possible. `match_status` records how each row was resolved (clean 1:1 match, or one of several disambiguation passes); `opeq_agrees` is a QA flag (does `BRANCH.OP_EQCODE` match the CIM `OpEqName`?) kept on every row for spot-checking. 95.5% of teids resolve to exactly one `branch_id`; the rest are in `unmatched_classified.csv`. Built by `build_teid_branchid_map.py`.

**`transformer_leg_map.csv`** — for transformers specifically: surfaces BOTH the high-side and low-side `BRANCH` rows for a given `teid` (the main map above only keeps one winner). Includes cases where the two legs share the same `teid`, and cases where one leg's `teid` is `NULL` in `BRANCH` and the sibling had to be found by name/bus-pair matching instead. Built by `build_transformer_leg_map.py`.

**`collapseid_fix_candidates.csv`** — recommended **database fixes**: `Line`/`Transformer` rows that look like the same physical element inserted into `BRANCH` more than once with no `collapseId` link recording the supersession. `old_branch_id` should get `collapseId` set to `recommended_collapseid`. Two confidence tiers — `confirmed_exact_duplicate` (identical `OP_EQCODE`) and `probable_renamed_duplicate` (same bus pair + same `ckt`, different name — e.g. a station-rename). Built by `find_collapseid_fix_candidates.py`.

**`teid_collision_candidates.csv`** — a **manual-review worklist**, not a fix list: `Line`/`Transformer` rows sharing a `teid` with something they don't match any validated pattern for (not a confirmed duplicate, not a legitimate transformer leg pair). These likely need the **`teid` value itself** corrected on one of the rows, but "unexplained" means "doesn't fit a pattern we've validated," not "confirmed wrong" — needs a human look. Built by `find_teid_collision_candidates.py`, which depends on the two files above already being current.

**`unmatched_classified.csv`** — the ~516 CIM `teid`s with no `BRANCH` row at all, classified by why: mostly transformer tertiary-winding stubs (3-winding CIM decomposition artifact) or generation-plant-internal collector equipment — neither is a real gap. Built by `analyze_unmatched.py`.

**`branch_default_status.csv`** — first-cut approximation of each branch's `default_status` (normally closed vs normally open), using `AW.dbo.ptoBranch` status across the last ~20 ERCOT Monthly Auction cases (2025-2026, via `AW.dbo.ptoFile`). Tallies `Closed`/`Open` per `branch_id` and takes the majority; `review_flag` is `clear_majority`, `mixed` (roughly even split — could be a genuinely normally-open device like a reactor/capacitor bypass or PST, or just a lot of sampled outages — needs a human look), or `no_pto_data` (zero coverage in the recent window, ~2.6% of branches). Explicitly a stopgap: doesn't dedupe bus-split rows within one snapshot, and will eventually be superseded by an in-service-date/outage-data-based approach. Built by `build_branch_default_status.py`.

**`teid_inservice_retirement_dates.csv`** — first-cut `in_service_date`/`retirement_date` per `teid`, inferred from `AW.dbo.toChangesAllIsos` outage records where `ReasonID` is `4` ("New Equipment Energization") or `9` ("Retirement of Old Equipment") -- the field the user originally pointed at (`outageTypeID`/`toOutageTypeId`) turned out to be NULL for every ERCOT row. Defaults to `1990-01-01` / `2099-12-31` when no matching outage exists. Method (see `../CLAUDE.md` for full narrative): cancelled/withdrawn/rejected/terminated requests are dropped first; actual dates are made "sticky" across a ticket's own revisions; events are cross-checked against `teid_branch_id_map.csv` on both `BranchId` and normalized `EquipmentName`/`OpEqName` (substring containment, not exact equality); consecutive events within 3 days collapse into one **chain**; per **ERCOT convention**, energization uses the chain's overall **end** date, retirement its first **start**; a retirement that predates an energization for the exact same device is corrected as a mis-tag. **Retirement is additionally cross-checked against `branch_default_status.csv`'s `implied_default_status`**: 83% of all resolved retirements initially contradicted a Closed status (recent, direct auction-model evidence) -- including single-ticket retirements a full decade old still showing 100% Closed today, and clusters of different teids sharing the exact same retirement timestamp (a signature of coordinated substation maintenance being tagged "Retirement," not real decommissioning). A confidently-contradicted retirement (`clear_majority` Closed, >=5 recent snapshots) is reverted to the default; a weaker contradiction is flagged `retirement_status_uncertain` rather than corrected. `review_flag` surfaces what's left needing a look: `multiple_confirmed_energization_events` / `multiple_confirmed_retirement_events` (2+ genuinely separate chains), `energization_planned_not_actualized` (weaker, planned-only evidence), `evidence_dropped_wrong_device` (zero surviving evidence, but only because real outage evidence existed for a different device), `retirement_status_uncertain` (retirement contradicts status but not confidently enough to auto-correct), `retirement_found_no_energization` (expected), and `teid_reused_after_retirement` (informational: genuine teid reuse across two devices whose names share no relation). Every teid still gets a best-guess date regardless of its flag -- the flagged subset is also written to `inservice_retirement_review_flags.csv`. Built by `build_inservice_retirement_dates.py`.

**`inservice_retirement_review_flags.csv`** — every row from `teid_inservice_retirement_dates.csv` with `review_flag != 'ok'` (658 teids as of the last run), split out into its own file so the ambiguous/informational cases can be reviewed separately from the ~94% that resolved cleanly. Same columns as the parent file.

**`multiple_energization_review.csv`** — ad hoc batch review of the `multiple_confirmed_energization_events` bucket: one row per (teid, chain) with date range, `BranchId`/`EquipmentName`, and sample `Notes`. Built by `review_multiple_energization_chains.py`; used to confirm the bundled-device pattern (see `teid=70365`) was rare in that bucket.

**`retirement_flags_investigation.csv`** — ad hoc raw-revision dump (ALL `ReasonID` values, not just 4/9) for the teids flagged `multiple_confirmed_retirement_events` or (formerly) `retirement_before_inservice`. Built by `investigate_retirement_flags.py`; used to test and rule out a TSP-reclassification hypothesis, and to trace the device-name evidence behind the mis-tag correction and `teid_reused_after_retirement` flag.

**`dampsse_default_status.csv`** / **`dampsse_default_status_fallback.csv`** — second-source `default_status` from ERCOT's DAM PSSE hourly models (`ercotDampsseTimeseries.inService`, 2-year window, dominant status wins). Per the user, DAM `inService` is a better status indicator than the auction snapshots. The main file covers teids mapped by exact normalized name (`branchNameRaw` ↔ `OP_EQCODE`); the fallback file covers teids recovered by `map_unmapped_dampsse_teids.py`'s fallback tiers. Built by `build_dampsse_default_status.py` (also caches DAM dims + the 2-year `inService` aggregate to `data/raw/` so follow-on mapping work is DB-free).

**`dampsse_fallback_mappings.csv`** / **`dampsse_unmapped_diagnosis.csv`** — the fallback teid→`ercotDampsseId` mapping tiers (substring name, station-pair, transformer leg-aware within both — filtered by Line/Transformer fileType) and the diagnosis of what still doesn't map (station-pair-ambiguous parallel elements, plus a handful genuinely absent from the DA model: GSU/tertiary stubs). Built by `map_unmapped_dampsse_teids.py`, DB-free from the `data/raw/` cache. Combined coverage: 10,816 of 10,927 teids (99.0%).

**`base_model_status_comparison.csv`** / **`base_model_outages_status_comparison.csv`** — status comparison of our final table against the user's PowerWorld base model exports (clean + outages cases), resolving each base-model row to a teid via format-classified labels (integer=teid, UUID=rdfid→CIM TeidMap). Built by `compare_base_model_status.py <export.csv>`. The intersection of the two disagreement sets (189 teids) is the robust review list.

## Background investigation (superseded by the above, kept for evidence)

**`duplicate_teid_groups.csv`** / **`duplicate_teid_groups_snowflake.csv`** — earlier investigation into *why* `BRANCH.teid` has duplicates at all, classified via `PTOBRANCH` bus-number agreement (`same_identity_reinserted` / `teid_collision_different_branches` / `insufficient_pto_data`, the last being most groups since `PTOBRANCH` only covers ~12.7% of `BRANCH` rows). SQL Server and Snowflake versions, kept both because the two sources disagree substantially on row/duplicate counts. Built by `analyze_duplicate_teids.py` / `analyze_duplicate_teids_snowflake.py`.

**`duplicate_opeqcode_classified.csv`** — early exploration of using `OP_EQCODE` to disambiguate 2-candidate duplicate `teid`s. The logic here was generalized and folded into `build_teid_branchid_map.py`'s resolution pipeline. Built by `analyze_duplicate_opeqcode.py`.
